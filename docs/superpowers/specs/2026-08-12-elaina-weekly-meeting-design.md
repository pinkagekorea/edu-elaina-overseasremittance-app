# 주간회의 (elaina) — 설계

작성 2026-08-12

## 왜

주간회의에서 매주 같은 것을 묻는다 — 지난주에 어디로 보냈나, 못 보낸 데는
어디고 왜인가, 언제 보낼 건가. 지금은 물어볼 근거가 앱에 없다.

## 먼저 확인한 것 — 왜 새 표가 필요한가

기존 원본 `edu_elaina_overseasremittance` 로는 주간 화면을 만들 수 없다.
실측한 사실:

| 확인 | 실제 |
|---|---|
| 송금일 컬럼 | 없다. `remit_month` 가 `'2026-08'` 같은 **월 단위 텍스트**뿐 |
| `created_at` | 서로 다른 값이 **2개** (`2026-08-05`, `2026-08-06`) — 일괄 적재 시각이지 송금일이 아니다 |
| 행의 단위 | **월 × 업체 합계**. `tx_count` 최대 4 — 한 행에 여러 건이 뭉쳐 있어 날짜로 못 쪼갠다 |
| 미송금 | 36행 전부 0 |

`created_at` 을 송금일로 쓰면 화면이 틀린 숫자를 자신 있게 보여주게 된다.
그래서 **송금 건별 표를 새로 만든다.**

## 무엇을 만드나

| 조각 | 하는 일 |
|---|---|
| `edu.elaina_monthly_baseline` | 지금 월별 표 36행의 사본. 딱 한 번 찍는다 |
| `edu.elaina_remittances` | 송금 건별 표. 앞으로 여기에 쌓는다 |
| 동기화 트리거 | 건별이 바뀌면 월별 표를 다시 계산 |
| 복구 함수 | 월별 표를 기준선으로 되돌린다 |
| 「주간회의」 카드 | 연도·주차 선택 · 송금/미송금 · 사유·예상일 입력 |

## 주 배정 — 생성 컬럼 한 줄

```
week_date = coalesce(paid_date, due_date)
```

보냈으면 **보낸 날**, 못 보냈으면 **보내기로 했던 날**. DB 가 계산하므로
화면과 어긋날 수 없고, 인덱스도 여기 건다. 주는 ISO 기준 월~일이고,
화면 기본값은 직전 주다.

## 두 표를 맞추는 규칙 — 한 줄

```
월별표(월, 업체) = 기준선(월, 업체) + Σ 건별(status='paid', 그 월, 그 업체)
```

**기준선이 있어야 하는 이유.** 건별 표는 비어 있는 채로 시작하고 월별 표에는
이미 8개월치 36행이 있다. 모집단이 다르다. 월별표를 건별합으로 *덮으면*
과거가 0 이 되고, 건별합을 월별표에 *더하면* 트리거가 두 번 돌 때마다 값이
불어난다. 기준선을 두면 식이 언제나 같은 값을 내므로(멱등) 둘 다 피한다.

- 건별에만 있는 (월, 업체) → 월별 표에 새 행을 넣는다
- 건별 합이 0 이 되고 기준선에도 없으면 → 그 행을 지운다 (원래 없던 행이다)
- 업체·날짜를 고치면 **옛 조합과 새 조합을 둘 다** 다시 계산한다

### 무엇이 합산되고 무엇이 아닌가

| 합산 | 손대지 않음 |
|---|---|
| `tx_count` · `usd_amount` · `cny_amount` · `paid_krw` | `uncleared_*` · `unpaid_*` |

미통관은 **통관** 정보인데 건별 표에 그런 칸이 없다. 없는 값을 지어내지 않고
기준선 값을 그대로 둔다.

**미송금 건은 월별 표에 넣지 않는다.** 「실제 송금액」은 실제로 나간 돈이고
미송금은 아직 안 나갔다. 미송금은 주간회의 화면에서만 산다. `unpaid` 를
`paid` 로 바꾸는 순간 트리거가 월별 표에 넣는다.

그래서 제약이 하나 붙는다: **`paid` 건은 원화(`krw`) 필수.** 월별 표의
「실제 송금액」에 넣을 값이 있어야 한다.

## 표

```
edu.elaina_remittances
  id             bigint identity PK
  vendor_name    text     not null
  currency       text     not null      -- 'USD' | 'CNY'
  amount         numeric  not null      -- 외화
  krw            numeric                -- paid 면 필수
  due_date       date     not null      -- 예정 송금일
  paid_date      date                   -- 실제 송금일 (unpaid 면 없음)
  status         text     not null      -- 'paid' | 'unpaid'
  unpaid_reason  text                   -- 미송금 사유
  expected_date  date                   -- 예상 송금일
  note           text
  week_date      date  generated always as (coalesce(paid_date, due_date)) stored
  created_by / created_at / updated_by / updated_at   -- 트리거가 찍는다
```

제약: `paid` ⇒ `paid_date` 있고 `krw > 0` · `unpaid` ⇒ `paid_date` 없음 ·
`amount > 0` · 통화는 둘 중 하나.

## 잠금

- `authenticated` 에 **SELECT·INSERT·UPDATE**. 정책은 원본 표와 같은 줄
  (`@pinkage.co.kr`) — 요약이 원본보다 넓게 보이면 안 된다.
- **DELETE 는 아무에게도 주지 않는다.** 잘못 넣은 건은 관리자 함수로만 지운다.
- 작성자·수정자·시각은 트리거가 찍는다. 화면이 보낸 값은 버린다.
- `anon` 은 표·함수 전부 권한 0.
- 동기화 트리거는 `postgres` 소유 `SECURITY DEFINER` 다. 월별 표는 소유자가
  `postgres` 이고 `FORCE RLS` 가 꺼져 있어 트리거가 쓸 수 있다. 화면은 여전히
  못 쓴다 (`authenticated` 에 쓰기 정책이 없다).

## 화면 — 별도 화면, 시트 두 장

대시보드와 성격이 달라 화면을 따로 쓴다. 머리말의 **주간회의** 버튼으로
들어가고 주소는 `?view=weekly` 다. 파일은 그대로 `index.html` 하나다 —
따로 쪼개면 로그인·서비스워커·PWA 설정이 두 벌이 된다.

```
[← 대시보드]                        [2026 ▾] [32주 ▾] [‹] [›]

주간회의  2026-08-03 ~ 2026-08-09      송금 2건 · 85,749,640원 · 미송금 1건
월~일 기준(ISO) · 기본은 직전 주

▸ 송금된 업체  2곳
 업체   │ 예정일 │ 송금일 │ 통화 │    금액 │      원화(원)
 성창   │ 08-04  │ 08-05  │ USD  │ 12,000.00 │  58,087,357
 JH     │ 08-06  │ 08-07  │ CNY  │ 85,000.00 │  27,662,283

▸ 미송금 업체  1곳
 업체   │ 예정일 │ 통화 │   금액 │ 미송금 사유    │ 예상 송금일
 하이썬 │ 08-06  │ USD  │ 9,500.00 │ [서류 미비  ] │ [2026-08-20]
                                                     [저장 (1줄)]
```

**송금 등록 폼은 두지 않는다.** 송금 실적은 시트에서 들어오고, 이 화면은
그것을 주 단위로 모아 보는 곳이다.

**고칠 수 있는 것은 두 칸뿐이다** — 미송금 사유·예상 송금일. 회의에서 적는
값이라 시트 안에서 바로 고치고, 바뀐 줄만 모아 한 번에 저장한다. 고친 칸은
테두리로 표시되고 저장 버튼이 바뀐 줄 수를 보여준다. 나머지 칸은 읽기 전용이다.

저장 결과는 **서버가 돌려준 줄 수로 판정한다.** RLS 가 막으면 오류 없이 0줄이
돌아오므로, 0줄이면 성공한 척하지 않고 실패로 알린다.

## 실패

조회 실패·저장 실패 모두 카드 안에서만 알린다. 전체 화면을 덮는
`showError` 는 쓰지 않는다 — 주간회의가 실패해도 나머지 화면은 멀쩡하다.

## 되돌리기

기준선이 원본 36행의 사본이므로, 문제가 생기면
`edu.elaina_restore_monthly_from_baseline()` 로 월별 표를 원상 복구한다.

## 입력 경로 — 아직 연결되지 않았다

건별 표를 채우는 것은 **구글 시트**로 정했다. 흐름은
`시트 → elaina_remittances → (트리거) → 월별 표 → 데일리 리포트` 이고,
지금까지 만든 기준선·동기화가 그대로 산다. 시트는 입력 경로만 대신한다.

아직 시트를 연결하지 않았다. 그래서 화면은 비어 있고, 그 사실을 화면 아래에
그대로 적는다 — 비어 있는 것과 고장난 것은 구분되어야 한다.

연결하려면 정해야 할 것: 시트 주소 · 열 이름 규칙 · 접근 방식(서비스 계정을
Edge 환경변수에 두는 쪽과, 시트를 웹에 게시해 CSV 로 읽는 쪽. 뒤쪽은 주소를
아는 누구나 송금 내역 전체를 볼 수 있다) · 가져오는 시점.

**사유·예상 송금일은 시트에서 가져오지 않는다.** 회의에서 앱에 적는 값이다.
시트는 송금 실적(사실)의 원천이고, 이 두 칸은 회의의 기록이다.

## 일부러 안 한 것

앱 안 등록 폼 (시트가 원천이므로) · 슬랙 알림 · 회의록 본문·참석자 ·
과거 이력 채워 넣기 (비어 있게 두고 앞으로 쌓는다) · 미통관 추적.

## 알려진 한계

- 건별 표는 비어 있게 시작한다. 시트를 연결하기 전까지 어느 주를 열어도 0건이다.
- 미통관(`uncleared_*`)은 건별 표에 정보가 없어 기준선 값에서 움직이지 않는다.
  월별 표에 새로 생긴 (월, 업체) 행의 미통관은 0 이다.
- 월별 표를 사람이 직접 고치면 기준선과 어긋난다. 다만 지금 월별 표에
  쓸 수 있는 것은 `postgres`/`service_role` 뿐이라 실질적으로 트리거가 유일한
  기록자다.
